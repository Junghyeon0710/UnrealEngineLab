## 1. 클린 코드란?

클린 코드는 단순히 코드가 짧거나 예쁘게 정렬된 코드를 의미하지 않는다.

**코드의 의도가 명확하고, 읽기 쉽고, 변경과 유지보수가 쉬운 코드**라고 생각한다.

특히 게임 개발은 기능 추가와 변경이 자주 발생하기 때문에 단순히 현재 잘 동작하는 코드보다 **나중에 안전하게 변경할 수 있는 코드**가 중요하다.

좋은 코드는 다음 질문에 쉽게 답할 수 있어야 한다.

- 이 코드는 무엇을 하는가?
- 왜 여기에 있는가?
- 수정하려면 어디를 변경해야 하는가?
- 수정했을 때 다른 기능에 얼마나 영향을 주는가?

<a id="meaningful-names"></a>

## 2. 명확한 이름 사용

변수, 함수, 클래스 이름만 보고도 역할을 어느 정도 이해할 수 있어야 한다.

### 개선 전

```cpp
int32 A;
int32 Cnt;

void Do();
```

### 개선 후

```cpp
int32 RemainingItemCount;

void AddItem();
void RefreshInventory();
```

복잡한 조건 역시 의미를 알 수 있는 이름으로 표현하는 것이 좋다.

### 개선 전

```cpp
if (ItemCount > 0 && PlayerLevel >= 10 && !bLocked && Player != nullptr)
{
    EquipItem();
}
```

### 개선 후

```cpp
if (CanEquipItem())
{
    EquipItem();
}
```

코드를 읽는 사람이 내부 조건을 하나씩 해석하지 않아도

> 아이템을 장착할 수 있는지 확인한다.

라는 의도를 바로 알 수 있다.

<a id="single-purpose-functions"></a>

## 3. 함수는 하나의 역할만 수행한다

개인적으로 클린 코드에서 가장 중요하다고 생각하는 부분이다.

많은 코드를 보다 보면 어떤 함수를 따라 들어갔을 때

> "이 로직을 왜 여기서 처리하지?"

라는 생각이 드는 경우가 있다.

함수 이름이 `AddItem()`이라면 **아이템을 추가하기 위해 필요한 작업에 집중해야 한다.**

```cpp
void UInventory::AddItem(const FItemData& NewItem)
{
    if (!CanAddItem(NewItem))
    {
        return;
    }

    Items.Add(NewItem);
    OnInventoryChanged.Broadcast();
}
```

여기서

```cpp
UpdateInventoryUI();
SaveInventory();
CheckQuest();
PlayAcquireSound();
```

까지 직접 처리하기 시작하면 `AddItem()`과 `Inventory`가 다른 시스템의 책임까지 가지게 된다.

### 개선 전

```cpp
void UInventory::AddItem(const FItemData& NewItem)
{
    Items.Add(NewItem);

    UpdateInventoryUI();
    SaveInventory();
    CheckQuest();
    PlayAcquireSound();
}
```

아이템이 추가되었다는 사실을 다른 시스템이 알아야 한다면 이벤트나 델리게이트를 사용할 수 있다.

```cpp
void UInventory::AddItem(const FItemData& NewItem)
{
    Items.Add(NewItem);
    OnInventoryChanged.Broadcast();
}
```

```text
UInventory
    │
    └─ OnInventoryChanged
            │
            ├─ InventoryWidget → UI 갱신
            ├─ SaveSystem      → 저장
            └─ QuestSystem     → 퀘스트 체크
```

이렇게 하면 `Inventory`는 자신의 역할인 **아이템 상태 관리**에 집중할 수 있다.

<a id="one-purpose-many-steps"></a>

## 4. 여러 함수를 호출한다고 여러 역할인 것은 아니다

"함수는 하나의 일만 해야 한다"는 것이

> 함수 안에서 다른 함수를 하나만 호출해야 한다.

는 의미는 아니다.

```cpp
void CookRamen()
{
    BoilWater();
    AddNoodles();
    AddSoup();
}
```

여러 함수를 호출하지만 목적은 하나다.

> 라면을 만든다.

게임 코드 역시 마찬가지다.

```cpp
void AddItem()
{
    ValidateItem();
    InsertItem();
    StackItem();
}
```

각 함수는 다른 작업을 하지만 모두 **아이템을 추가한다**는 하나의 목적에 포함된다.

중요한 것은 함수 호출 개수가 아니라

> 이 함수의 목적을 한 문장으로 설명할 수 있는가?

이다.

<a id="reduce-nesting"></a>

## 5. 중첩과 복잡도를 줄인다

조건문이 깊어질수록 코드 흐름을 파악하기 어려워진다.

### 개선 전

```cpp
if (Player)
{
    if (Item)
    {
        if (!Item->IsLocked())
        {
            EquipItem();
        }
    }
}
```

### 개선 후

```cpp
if (!Player)
{
    return;
}

if (!Item)
{
    return;
}

if (Item->IsLocked())
{
    return;
}

EquipItem();
```

Early Return을 사용하면 예외 조건을 먼저 제거하고 정상적인 처리 흐름에 집중할 수 있다.

다만 무조건 Early Return을 사용하기보다는 **어떤 방식이 현재 함수의 흐름을 가장 쉽게 이해할 수 있게 하는가**를 기준으로 판단하는 것이 좋다.

<a id="avoid-duplication"></a>

## 6. 중복은 줄이되 억지로 합치지 않는다

같은 규칙이 여러 곳에 반복되면 수정할 때 실수가 발생하기 쉽다.

### 개선 전

```cpp
Gold -= ItemPrice;
OnGoldChanged.Broadcast();
```

```cpp
Gold -= UpgradePrice;
OnGoldChanged.Broadcast();
```

같은 규칙이라면 하나의 함수로 관리할 수 있다. 아래 예제는 차감할 금액과 잔액 검증을 마친 상황을 가정한다.

```cpp
void UGoldManager::ConsumeGold(int32 Amount)
{
    Gold -= Amount;
    OnGoldChanged.Broadcast();
}
```

하지만 코드 모양이 비슷하다는 이유만으로 무조건 합치는 것도 좋지 않다.

현재는 같은 코드여도 **서로 다른 이유로 변경될 가능성이 있다면 분리되어 있는 편이 더 나을 수 있다.**

<a id="class-responsibilities"></a>

## 7. 클래스의 책임과 의존성을 관리한다

클래스 역시 함수와 마찬가지로 주요 책임이 명확한 것이 좋다.

예를 들어 `Inventory`가 다음 기능을 모두 직접 처리한다고 생각해보자.

```text
Inventory
 ├─ 아이템 데이터
 ├─ UI
 ├─ 서버 통신
 ├─ 저장
 ├─ 사운드
 └─ 퀘스트
```

기능이 늘어날수록 클래스가 커지고 다른 시스템과의 의존성도 증가한다.

가능하면 역할을 구분한다.

```text
Inventory
    → 아이템 상태 관리

InventoryWidget
    → 화면 표시

InventoryNetwork
    → 서버 통신

InventorySaveSystem
    → 저장
```

여기서 중요한 개념이 **응집도와 결합도**다.

### 높은 응집도

관련 있는 기능은 함께 둔다.

```text
Inventory

AddItem()
RemoveItem()
FindItem()
GetItemCount()
```

모두 인벤토리 상태와 관련된 기능이다.

### 낮은 결합도

한 클래스가 필요 이상으로 많은 다른 시스템을 알지 않도록 한다.

좋은 구조는 일반적으로

> **높은 응집도 + 낮은 결합도**

를 목표로 한다.

책임을 나눌 때는 다음 질문도 도움이 된다.

> 이 코드들은 같은 이유로 변경되는가?

`AddItem()`, `RemoveItem()`, `StackItem()`은 인벤토리 규칙 변경이라는 같은 이유로 수정될 가능성이 높다.

반면 `RefreshUI()`, `Save()`, `PlaySound()`는 각각 UI, 저장 방식, 사운드 정책처럼 서로 다른 이유로 변경된다.

<a id="useful-comments"></a>

## 8. 주석도 유지보수를 위한 코드의 일부라고 생각한다

흔히

> 좋은 코드는 주석 없이도 이해할 수 있어야 한다.

라고 이야기한다.

물론 변수명과 함수명을 명확하게 작성해서 코드 자체만으로 최대한 이해할 수 있게 만드는 것이 좋다.

하지만 개인적으로는 **적절한 주석이 있는 코드를 선호한다.**

내가 작성한 코드라도 6개월 뒤 다시 보면 당시 왜 이런 처리를 했는지 기억하기 어려운 경우가 많다.

이럴 때 주석을 통해 당시의 의도나 제약사항을 빠르게 파악할 수 있다면 오히려 유지보수에 도움이 된다고 생각한다.

### 불필요한 주석

```cpp
// 아이템 개수를 1 증가시킨다.
ItemCount++;
```

코드만 봐도 알 수 있는 내용을 그대로 설명하고 있다.

### 도움이 되는 주석

```cpp
// 서버 PRESET_IDX가 1부터 시작하므로 배열 인덱스로 사용할 때 1을 뺀다.
const int32 PresetIndex = PresetIndexFromServer - 1;
```

좋은 주석은 주로 다음 내용을 설명한다.

- 왜 이렇게 구현했는가?
- 특수한 처리의 이유가 무엇인가?
- 외부 데이터나 서버의 규칙이 있는가?
- 변경할 때 주의해야 할 제약사항이 있는가?

따라서 주석이 없는 코드가 좋은 코드라기보다는

> **코드 자체로 동작을 이해할 수 있고, 주석을 통해 의도와 이유까지 빠르게 파악할 수 있는 코드**

가 좋은 코드라고 생각한다.

<a id="avoid-overengineering"></a>

## 9. 과도한 분리와 추상화도 피한다

클린 코드를 만든다고 모든 것을 함수, 클래스, 인터페이스, 이벤트로 나누는 것도 좋지 않다.

예를 들어

```cpp
Health -= Damage;
```

면 충분한 상황에서

```text
IDamageReceiver
DamageProcessor
DamageContext
DamageResolver
DamageDispatcher
DamageEventHandler
```

까지 만드는 것은 오히려 코드의 이해 비용을 증가시킨다.

함수 역시 단순히 작게 만들기 위해 지나치게 나누면 호출 흐름을 따라가기 어려워질 수 있다.

함수를 분리할 때는 다음과 같은 기준을 생각한다.

- 별도의 의미가 있는가?
- 이름을 붙이면 코드가 더 이해하기 쉬워지는가?
- 재사용할 필요가 있는가?
- 독립적으로 변경될 가능성이 있는가?

결국 중요한 것은 **많이 나누는 것이 아니라 적절하게 나누는 것**이다.

<a id="trade-offs"></a>

## 10. 클린 코드에도 Trade-Off가 있다

어떤 방식도 항상 정답은 아니다.

예를 들어 이벤트는 시스템 간 결합도를 낮출 수 있지만

```text
누가 이벤트를 받고 있는지 찾기 어려움
호출 흐름을 추적하기 어려움
디버깅 난이도가 증가할 수 있음
```

이라는 단점이 있다.

반대로 직접 호출은 어느 정도 결합도가 생기지만

```text
호출 흐름이 명확함
디버깅하기 쉬움
코드를 따라가기 쉬움
```

이라는 장점이 있다.

따라서 중요한 것은

> 어떤 패턴을 사용했는가?

보다

> 왜 이 구조를 선택했는가?

이다.

<a id="checklist"></a>

## 11. 코드 작성 시 확인할 것

코드를 작성하거나 리뷰할 때 다음 정도를 확인한다.

### 함수

- 함수의 역할을 한 문장으로 설명할 수 있는가?
- 함수 이름과 실제 동작이 일치하는가?
- 예상하지 못한 다른 책임이 섞여 있지 않은가?
- 조건문과 중첩이 지나치게 복잡하지 않은가?

### 클래스

- 클래스의 주요 역할이 명확한가?
- 서로 관련 있는 기능이 모여 있는가?
- 다른 시스템을 필요 이상으로 많이 알고 있지 않은가?

### 유지보수

- 6개월 뒤 다시 봐도 빠르게 이해할 수 있는가?
- 변경 이유를 주석이나 코드에서 파악할 수 있는가?
- 기능 하나를 수정하기 위해 너무 많은 코드를 수정해야 하지는 않는가?
- 필요 이상으로 복잡하게 추상화되어 있지는 않은가?

<a id="summary"></a>

## 12. 핵심 정리

개인적으로 클린 코드에서 가장 중요하게 생각하는 것은

> **하나의 함수가 하나의 명확한 역할을 수행하는 것**

이다.

함수 이름을 보고 들어갔는데 전혀 예상하지 못한 시스템의 처리까지 이루어지고 있다면 코드를 이해하기도 어렵고 변경했을 때의 영향 범위도 커진다.

따라서 함수와 클래스가 자신의 책임에 집중하도록 만들고, 필요하다면 이벤트나 델리게이트 등을 이용해 다른 시스템의 반응을 분리하는 것이 좋다고 생각한다.

그와 함께 다음을 중요하게 생각한다.

```text
명확한 이름
    ↓
명확한 책임
    ↓
낮은 복잡도
    ↓
높은 응집도 / 낮은 결합도
    ↓
변경하기 쉬운 구조
```

그리고 클린 코드를 위해 무조건 코드를 잘게 나누거나 이벤트, 인터페이스를 사용하는 것이 정답은 아니다.

결국 좋은 코드의 기준은

> **코드를 읽었을 때 의도를 쉽게 이해할 수 있고, 시간이 지난 뒤에도 빠르게 파악하여 안전하게 수정할 수 있는가**

라고 생각한다.

<a id="my-perspective"></a>

## 13. 내가 중요하게 생각하는 클린 코드

제가 클린 코드에서 가장 중요하다고 생각하는 것은 **하나의 함수가 하나의 역할만 수행해야 한다는 점**입니다.

많은 코드를 보다 보면 특정 함수를 따라 들어갔을 때, “이 로직을 왜 여기서 처리하지?”라는 생각이 드는 경우가 많았습니다.

예를 들어 `AddItem()`이라는 함수라면 아이템을 추가하는 데 필요한 처리만 담당하는 것이 좋다고 생각합니다. 이후 UI 갱신, 퀘스트 처리, 저장과 같이 다른 시스템에서 처리해야 하는 작업까지 직접 수행하기보다는, 이벤트나 델리게이트를 통해 아이템이 추가되었다는 사실만 알리고 각 시스템이 필요한 동작을 수행하도록 분리하는 방식이 더 적절하다고 생각합니다.

이렇게 하면 함수의 역할이 명확해지고, 코드를 따라갈 때도 예상하지 못한 동작을 발견할 가능성이 줄어듭니다.

또 흔히 **“좋은 코드는 주석 없이도 이해할 수 있어야 한다”**고 이야기하지만, 개인적으로는 적절한 주석이 있는 코드를 선호합니다.

물론 변수명과 함수명만으로 코드의 의도가 충분히 드러나는 것이 가장 좋습니다. 하지만 제가 직접 작성한 코드라도 6개월 뒤 다시 보게 되면 당시의 의도나 특수한 처리 이유까지 바로 기억하기는 어렵습니다.

이럴 때 주석을 통해 “왜 이렇게 구현했는지”, “어떤 제약 때문에 이런 처리가 들어갔는지”를 빠르게 파악할 수 있다면 오히려 유지보수에 도움이 된다고 생각합니다.

따라서 저는 **주석이 없는 코드가 좋은 코드라기보다는, 코드 자체로 동작을 이해할 수 있고 주석을 통해 그 코드의 의도와 이유까지 빠르게 파악할 수 있는 코드가 좋은 코드**라고 생각합니다.
